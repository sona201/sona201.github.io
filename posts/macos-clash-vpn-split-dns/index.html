在 macOS 上让企业 VPN 与 Clash 共存

记录 macOS 企业 VPN 与 Clash 共存的配置过程，以及 Claude 规则前置、服务 DNS 策略补齐、订阅更新和实际连接验证。

网络 2026-10-21 阅读时长: 14 分钟
阅读辅助

我的 Mac 需要同时访问公司内网、国内网站和海外服务。在家要连接企业 VPN，在公司使用办公网络；个人代理原先使用 Shadowrocket。麻烦出在切换网络时：有时公司页面打不开，有时多个网站同时异常，重开两个客户端后又恢复了。

排查中还遇到了另一个问题：关闭代理测速能到两百多 Mbps，代理测速页面上却曾看到约 36 Mbps。最初很容易把这些现象归到同一个原因，但实际涉及物理链路、VPN 路由、DNS、代理节点和测速方法。

最后采用的组合是 企业 VPN 保持公司要求的模式，Clash 使用系统代理，TUN 关闭，并只给 Clash 内部增加 DNS 分流。公司规则保存在本地，节点订阅单独更新。本文记录这套配置的形成过程，以及每项测试能说明什么。10 月 22 日，又继续调整了 Claude 的规则顺序，并补齐常用服务的 DNS 策略；两轮修改的测试结果分开记录。

文中的公司域名、内网地址和服务器地址均使用示例值；不包含原始配置、订阅链接或账户截图。配置行为以本次使用的 Clash Verge Rev 2.5.8 和 Mihomo v1.19.32 为准。

先分清系统代理和 VPN 的职责

企业 VPN 被固定在全局模式，客户端不能切换为仅接管内网的模式。我能调整的是个人代理如何参与这条链路。

接管方式 作用范围 与企业 VPN 共存时需要留意的地方
系统代理 由遵守系统代理设置的应用把请求交给本地代理端口 部分终端程序和应用不会自动遵守，需要单独配置或显式指定代理
TUN 通过虚拟网络接口接收被路由到该接口的流量 会增加路由和 DNS 接管关系，需要与企业 VPN 一起分析

这次把 Clash 的系统代理设为 127.0.0.1:7897，保持 TUN 关闭。企业 VPN 继续负责公司的网络接入，Clash 根据规则选择直连或个人节点。系统代理、TUN 决定流量如何进入客户端，规则模式则决定进入后的流量如何出站。Clash Verge Rev 名词解释

这里有一个容易误解的地方：Clash 的 DIRECT 只表示不经过它的代理节点，连接仍然遵循 macOS 的路由。 企业 VPN 开启后，即使某个请求命中 DIRECT，也可能继续经过 VPN。反过来，Clash 连接个人节点的那条 TCP 连接也可能被 VPN 承载。下面的命令能查看路由表为目标选择的接口；实际连接还可能受接口绑定或 VPN 策略影响，不能只看策略组名字。

选择 Clash Verge Rev，主要是为了把本地规则、节点订阅和运行配置分别管理，并通过 API 验证实际命中。已有节点能继续使用，本次没有通过购买另一个客户端解决问题。Shadowrocket 保留作备用，验证 Clash 独立工作时则将它断开，避免把备用客户端提供的 DNS 或路由误认为 Clash 自身的能力。

迁移时把节点和本地规则分开

迁移后的配置包含一个节点订阅、19 个策略组和17 个规则集。节点通过 HTTP provider 每小时更新，规则集每天更新；公司域名和个人覆盖规则留在本地工作配置中。

这样刷新节点订阅时，不需要重新编辑公司内网规则，也不会因为订阅模板更新而丢掉本地调整。实际还检查了 provider 的更新时间、更新请求结果，以及重开客户端后策略组选择是否保留。

这套规则最终按下面的优先级处理流量：

优先级 匹配对象 处理方式
最前面 公司域名、localhost、列出的 IPv4 私有网段 DIRECT
接着 已单独验证的域名覆盖 进入指定策略组或精确直连
再往后 海外服务规则集 对应服务组或通用代理组
后面 国内域名、国内 IP、局域网规则 本地直连
最后 未匹配流量 兜底代理组

Mihomo 按规则顺序匹配；域名规则提前命中后，不会再由后面的国内 IP 规则改判。IP-CIDR 中的 no-resolve 表示不要为了这一条规则主动解析域名，并不表示后面的规则也不会解析。Mihomo 路由规则

公司域名同时配置了系统代理绕过列表和 Clash 内部的 DIRECT 规则。前者服务于遵守 macOS 代理设置的应用；后者也覆盖显式把请求交给 Clash 的程序。两层各有用途。

规则仓库和客户端如何配合

blackmatrix7/ios_rule_script 提供适配不同客户端的规则和相关脚本；本次使用的是其中的规则数据，并结合了 Loyalsoldier 的集合。haoel.github.io 则提供代理部署和网络优化的思路。它们可以作为配置来源与排查参考，不能直接替代本机的 VPN、路由和 DNS 验证。

服务端检查确认已有 VLESS Reality Vision、TCP 传输以及 BBR 和 fq。没有为这次问题继续叠加传输协议或多路复用：先确定慢在哪一段，再决定是否改服务端。

把 36 Mbps 拆成可以验证的问题

首先检查本地链路。有线网络那次故障中，当前网络位置缺少实际 USB 网卡对应的服务，旧服务绑定的接口已不存在。补齐服务并获取 DHCP 地址后，有线恢复，协商结果为 100baseTX full-duplex。

这个结果说明当时那条以太网链路的协商速率是 100 Mbps，不是运营商套餐的上限。Wi-Fi 显示的连接速率也属于无线链路指标，不能直接当作应用下载速度。服务器面板里的每月流量额度则是累计传输量，与 Mbps 带宽又是两个单位。

后续连接环境发生过变化，另一次有线记录已是千兆全双工，因此不能把下面超过 100 Mbps 的结果套到前述百兆链路上。换不同目标做限量测试后，也发现“代理固定只能跑 36 Mbps”的解释并不成立：

测试 当时结果 可以说明的范围
Cloudflare 页面完整测试 下载约 142 Mbps，上传约 44.6 Mbps 该次完整页面测试的结果
同一页面的 1 MB 阶段 中位数约 35.7 Mbps 小文件阶段可能明显低于完整结果
Mac 经代理下载 Cloudflare 测试文件 约 134 Mbps 当时代理路径可以超过 36 Mbps
Apple 限量双连接下载 直连约 186 Mbps，代理约 165 Mbps 同一目标下代理有开销，但并非固定 36 Mbps
VPS 本机短时入站下载 约 1.47 Gbps 服务器在该短样本中能够超过千兆

这些不是同一轮测试的所有分支，不能拼成一张精确的带宽损耗图。最后一项也没有证明 VPS 套餐的端口上限，更不能保证从家里到服务器的跨境链路达到同样速度。

测速还要检查 HTTP 状态码。一次多连接样本拿到的是 403，应作为无效吞吐样本排除；测速网页里的 WebRTC 或 UDP 指标，也不能直接当作 VLESS TCP 隧道的丢包率。

DNS 结果不同是否就会让代理变慢

针对 Claude 和 Anthropic，做过一轮相邻的企业 VPN 开启、关闭、重新开启测试。过程中没有清理 DNS 缓存，也没有修改代理配置。

结果很明确：VPN 开启时，系统解析出现一组特定 CNAME 和地址；关闭后恢复为公共解析结果；重新开启后又回到前一组。同期直接查询家庭路由器和通过代理查询公共 DoH，返回的仍是公共结果。

这说明差异与 VPN 启用后的 DNS 路径 有关。它还不足以说明是客户端 Bug、恶意污染，或之前整机断网的根因。

接下来保持 Host、SNI 和证书校验不变，对不同地址实际建立连接。在当时的正常 Clash 代理路径上，Anthropic 普通域名请求与固定公共 IP 请求的首字节耗时中位数分别约为 804 ms 和 807 ms；Claude 为 801 ms 和 794 ms，差别很小。

还有一个更容易误判的现象：连接面板里显示过某个解析地址，正常域名请求却能成功；强制代理节点连接这个地址时反而发生 TLS 错误。对于保留域名的 VLESS TCP 请求，目标可能交给远端继续解析；实际行为还受 metadata 状态影响。因此，单看客户端的 destinationIP，不能证明服务器最终拨号的就是这个地址。Mihomo v1.19.32 VLESS 实现、metadata 处理

另一轮在 VPN 关闭时，把 Mac 经过代理的请求与 VPS 本机请求放在同一时段比较：

目标 Mac 经代理的首字节耗时 VPS 本机的首字节耗时
Anthropic trace 约 818 ms 约 43 ms
Claude trace 约 801 ms 约 28 ms

Mac 到节点端口的 TCP 建连中位数约 195 ms；同一连接复用后，请求耗时从约 787 ms 降到约 198 ms、192 ms。这个组合更支持继续检查客户端到节点的链路和连接建立成本，而不是直接给目标网站固定 IP。这里测的是小型 HTTP trace 请求，不是模型首 token 时间。

只给 Clash 增加内部 DNS 分流

10 月 20 日先增加了一层 Clash 内部 DNS 分流，目的是明确不同域名的解析路径。它没有把整台 Mac 的 DNS 都改成交给 Clash，也不以提高所有网站速度为前提。

第一版采用的分工是：

  • 公司域名、局域网域名和未匹配域名继续用 system。
  • 国内域名集合使用国内 DNS。
  • Claude 相关域名通过 ClaudeAI 查询境外 DoH，其他已知境外域名经 DNS_Proxy 查询。
  • 节点域名单独配置直接可用的解析器，避免“先有代理才能查 DNS、先查 DNS 才能连接代理”的循环。

明确走代理的域名为什么还会先查 DNS

基础配置落地后，我继续读了 Sukka 的代理环境中的 DNS 解析行为和DNS 配置技巧。其中一个细节值得回到自己的配置里看：显式代理请求已经带着域名，如果能直接命中域名代理规则，本地就不必先为 IP 分流查询一次 DNS。

对照运行规则后，发现排在前面的 YouTube 集合混有三条没有 no-resolve 的 IP 规则。一个带域名、尚无目标 IP 的请求，如果没有命中前面的域名项，就会在这里尝试解析。claude.ai 和 anthropic.com 当时还依赖后面的 Claude 集合，因此到达自己的规则前，已经多了一次本地 DNS 等待。此前前置的 claude.com 等五个后缀不走这条路径。

于是 10 月 22 日只增加了前面列出的两条域名规则，没有重排原有 40 条规则，也没有把所有 IP 规则一律改成 no-resolve。修改后共 42 条：公司和私网优先级不变，Claude 的两个主域名能更早进入 ClaudeAI；末尾的国内 IP 判断仍然保留。

这次改的是业务流量规则的位置。Claude 的七个 DNS 后缀策略在第一版就已存在，并不是又新增了一套 Claude DNS。

让服务规则和 DNS 策略对应起来

再看其他服务时，发现“流量会走代理”也不代表“需要本地解析时一定查海外 DNS”。例如 api.statsig.com、featuregates.org 已在 OpenAI 服务规则中，却不在当时的通用海外 DNS 集合中；如果规则匹配触发解析，它们仍会使用默认的 system。

服务集合可能有重叠，所以 DNS 策略也沿用业务规则的顺序：YouTube、Google、GitHub、Spotify、Netflix、HBO、Bing、OpenAI、已有的 Claude、Disney，之后才是通用海外集合和国内集合。公司域名的 system 策略仍在前面。现有 Telegram 集合只有 IP，没有作为域名 DNS 策略加入。

这也意味着 google.cn、bing.com.cn 等已被服务规则覆盖的域名，按照对应服务组解析。普通国内网站继续使用国内 DNS，不能把结果概括成“所有 .cn 都使用国内 DNS”。默认未知域名仍为 system，节点域名的独立解析器、系统 DNS 和 TUN 设置均未改变。Mihomo DNS 策略说明

对照请求是否真的少了一次解析

这轮测试让正式 Clash 的 7897 和 1053 继续工作，旧、新配置分别在临时代理端口 17897 和 DNS 端口 11053 上运行，控制接口、缓存和规则文件也独立。等规则完整加载后，先发送带域名的 Claude、Anthropic 请求，再做显式 DNS 探针，避免先把待测域名查进缓存。

旧实例出现了相应的本地 DNS 查询，最终命中 Claude 规则集；新实例直接命中 DomainSuffix(claude.ai) 和 DomainSuffix(anthropic.com)，这两次请求期间没有对应的本地解析日志。下面是这组相邻单次请求的 curl 总耗时：

请求 原配置 前置规则后
Claude trace 1.699 秒 0.817 秒
Anthropic trace 1.025 秒 0.823 秒

这些日志支持的是：本次测试路径少了一次为规则匹配而进行的本地解析。远端仍可能需要解析域名，也不能由两个样本推导长期平均提速。正式配置热加载后的复测里，Claude 又耗时约 2.10 秒、Anthropic 约 0.87 秒，链路本身仍会波动。

正式验证中，公司入口通过系统路径和显式代理均返回 302；Claude、Anthropic、GitHub、百度、B 站返回 200，Google 返回 204。14 组 DNS 检查通过，包括上述九项服务的代表域名、OpenAI 的两个补漏域名及国内和公司域名；连接记录中也看到了九个服务组各自的 DoH 连接。这覆盖了 DNS 和小请求连通性，没有替代完整登录或流媒体播放测试。

配置通过校验后，以热加载方式应用，Clash 核心进程和启动时间没有改变。原规则顺序、公司覆盖、策略选择、节点每小时更新和规则集每天更新都保留，系统 DNS、系统代理与 TUN 状态也与修改前一致。

这次仍保留 redir-host 和系统代理模式，没有为了使用 Fake IP 改成整机接管。Sukka 关于 DNS、CDN 和 Fake IP 的文章帮助区分了不同接管场景，但本机这次可直接验证的问题，是规则顺序造成的额外等待。

此前在内部 DNS 关闭时，做过保持 Clash 进程不变、反复关闭和连接企业 VPN 的测试，公司内网和外网请求能够恢复。内部 DNS 启用后的重连测试被中断；10 月 22 日的优化又是在公司网络验证，没有开关企业 VPN，因此这项验证仍未完成。

接下来要在允许连接企业 VPN 的环境里，保持 Clash 运行，记录关闭、重连后的系统解析器、路由和公司入口恢复时间。还需要把新建请求与已经建立的长连接分开看，确认切换时是否只要等待恢复，还是仍有需要处理的状态。
